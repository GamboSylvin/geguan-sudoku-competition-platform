### New feature — "Delete competition" (BLD-050), DECIDED — **BUILT and verified**

Raised by the project owner after manual testing: "tellement de compétitions… je n'ai pas 15 jours à attendre avant que ça ne disparaisse" (too many test competitions, no 15 days to wait for them to vanish) — and the existing purge genuinely would not have helped: it never deletes the `Competition` row (keeps setup/questions/judges on purpose, RES-004) and only fires after `FINISHED`/`CANCELLED` + 15 days, which most test competitions never reach. **Scope, confirmed by the project owner (asked directly: full delete vs. purge-now-keep-shell) — full hard delete.** `DELETE /api/competitions/:id` (controller-only) removes the `Competition` and literally everything belonging to it — structure, questions, judge *assignments* (not the reusable `Judge` rows), schools, teams, participants, accounts, attempts, results, rankings, corrections, audit rows, its purge schedule — a strict superset of the 15-day purge's scope.    - **Fix shape, not fully prescribed — this needs real design, not a one-line patch:** `listRoundQuestions` needs a `categoryId` parameter (join through `Question.questionSet.categoryId`); the reconnect path (`gameplay.service.ts`) passes `participation.categoryId` — trivial. The round-start broadcast needs to become **per-category**: `startActivePhaseFromTimer` must build one payload per category (the competition's categories are a plain `prisma.competitionCategory.findMany({ where: { competitionId } })` query — no need to reach into another module for this) and the gateway must deliver each to that category's audience only, which likely means each `/player` socket joining a category-scoped room at connect time (the handshake already resolves `participantId`; resolving the participant's `categoryId` at the same time and joining e.g. `category:${categoryId}` alongside the existing `tabletRoom` join is the natural extension of the pattern already there) rather than broadcasting to everyone and hoping the client filters — the client currently doesn't, and even if it did, that would still leak question content over the wire to players who should never see it.
2. **Minor — a misleading error message.** `GET /api/judges/me` (a judge checking their own assignment, `identity/judge.controller.ts` line ~114) and the judge-management endpoints (create/list/delete, controller-only) share one error code and message: `judge.forbidden` / *"Only a controller can manage judges."* (`en.ts` line 47). Needs its own error code (e.g. `judge.meRequiresJudgeRole`) and message in both `en.ts`/`zh.ts`, not a shared one.
